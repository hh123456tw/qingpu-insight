# 青埔智價（Qingpu Insight）產品與系統設計規格

- 日期：2026-07-19
- 狀態：已完成口頭設計審核，待使用者審閱書面規格
- 目的：求職作品集、自用房價分析工具，保留未來正式上線能力
- 地理範圍：桃園機場捷運 A17、A18、A19 三個生活圈
- 住宅範圍：中古屋與預售屋，分開分析與建模

## 1. 摘要

青埔智價是一套以官方實價登錄為核心的房市分析與 AI 估價平台。使用者可在混合首頁查看 A17～A19 市場地圖與行情，或輸入物件條件和目前開價，取得合理單價、總價區間、相似成交案例、模型可信度及影響價格的主要因素。

本專案同時展現 AIPE04 課程中的 Python、Pandas、網路資料取得、特徵工程、Scikit-learn、MySQL、Flask、RESTful API、HTML、JavaScript、資料視覺化、Docker、MLOps 與大型語言模型應用。生成式 AI 只負責整理既有模型證據，不自行產生價格或成交紀錄。

## 2. 目標與非目標

### 2.1 目標

1. 提供 A17、A18、A19 中古屋與預售屋的市場趨勢、交易量、價格分布和熱區。
2. 依使用者輸入條件估算合理單價、不含車位房價、車位價值及合理總價區間。
3. 顯示相似成交案例、模型版本、資料日期、估價可信度和影響價格的因素。
4. 建立可重現、可測試、可透過 Docker 啟動的資料與模型流程。
5. 讓面試官能在五分鐘內理解問題、資料、模型、產品價值及限制。
6. 保留定期更新、雲端部署、收藏、通知與會員功能的擴充空間。

### 2.2 第一版非目標

1. 不涵蓋整個桃園或全台房市。
2. 不保證未來房價漲跌，也不代替估價師、房仲或財務顧問。
3. 不建立付費、會員或房仲後台。
4. 不大量或定期爬取售屋網站。
5. 不為追求技術複雜度而強制使用深度學習。
6. 不讓 LLM 修改模型估值或杜撰資料。

## 3. 使用者與核心流程

### 3.1 主要使用者

- 想了解青埔行情的自住買方。
- 想判斷特定物件開價是否合理的專案擁有者。
- 評估候選人資料工程、機器學習與全端能力的面試官。

### 3.2 核心流程 A：市場分析

1. 使用者選擇中古屋或預售屋。
2. 使用者選擇 A17、A18、A19 或三區比較。
3. 系統顯示中位單價、交易量、價格分布、時間趨勢和地圖熱區。
4. 使用者可依交易期間、坪數、建物類型與房數篩選。
5. 使用者可查看近期成交及資料更新時間。

### 3.3 核心流程 B：條件估價

1. 使用者選擇中古屋或預售屋。
2. 輸入生活圈、坪數、屋齡、樓層、總樓層、格局、車位及目前開價等欄位。
3. 系統驗證輸入並建立與訓練階段一致的特徵。
4. 系統呼叫對應模型，輸出合理單價及總價區間。
5. 系統查詢相似成交案例並產生特徵解釋。
6. 系統比較目前開價與估價中位數，標示偏低、合理或偏高。
7. 選配的 LLM 將上述結構化證據整理成白話摘要。

## 4. 資料設計

### 4.1 官方核心資料

核心成交資料使用內政部不動產實價登錄批次資料。官方資料集包含買賣、預售屋與租賃交易的實價及主要屬性，頁面目前標示每月 1、11、21 日發布，授權為政府資料開放授權條款第 1 版。

- 實價登錄批次資料：https://data.gov.tw/dataset/77051
- 下載入口：https://plvr.land.moi.gov.tw/DownloadOpenData

車站位置使用桃園捷運官方站點資料及桃園市政府開放的捷運出口座標。

- A17：https://www.tymetro.com.tw/tymetro-new/tw/_pages/travel-guide/A17
- A18：https://www.tymetro.com.tw/tymetro-new/tw/_pages/travel-guide/A18
- A19：https://www.tymetro.com.tw/tymetro-new/tw/_pages/travel-guide/A19
- 出口座標：https://data.gov.tw/dataset/45546

### 4.2 售屋資料政策

第一版不定期爬取售屋網站。使用者手動輸入物件條件與目前開價，成交行情和模型訓練只依賴官方資料。未來若加入售屋網址解析，必須先確認網站使用條款、robots 規則、資料授權及合理的請求頻率；解析失敗時仍須支援手動輸入。

### 4.3 生活圈判定

1. 初步保留桃園市中壢區與大園區住宅交易。
2. 將可用地址或區段資料轉為座標，並保存定位來源與可信度。
3. 只納入距離 A17、A18 或 A19 任一站兩公里內的紀錄。
4. 同時落入多個範圍時，歸入直線距離最近的站點。
5. 保存距離三站的公尺數；模型使用連續距離，不只使用生活圈類別。
6. 無法可靠定位的紀錄不進入地理模型，但可保留於原始資料與品質報告。

### 4.4 資料分層

- `raw`：官方原始檔、下載時間、來源與校驗資訊，不覆寫。
- `clean`：格式標準化、重複排除、缺失與異常標記。
- `geo`：座標、定位可信度、最近站點、距離與周邊設施。
- `feature`：模型可直接使用且有版本的特徵資料。
- `prediction`：輸入、模型版本、預測區間、可信度與建立時間。

### 4.5 主要特徵

- 交易年月及近期市場水準。
- A17／A18／A19 生活圈及各站距離。
- 建物移轉面積、主建物面積、房廳衛與建物類型。
- 屋齡、所在樓層、總樓層及樓層比例。
- 電梯、管理組織、主要建材與用途。
- 車位類型、車位面積及可分離的車位價格。
- 學校、公園、YouBike、商場與醫療設施的距離或一定半徑內數量。
- 中古屋可加入社區近期成交統計；預售屋可加入建案近期成交統計。

## 5. 模型設計

### 5.1 模型隔離

中古屋與預售屋使用不同的清理規則、特徵管線、模型、評估報告與版本。兩者可在介面比較，但不可混用一個正式估價模型。

### 5.2 預測目標

模型優先預測不含車位的每坪單價，再估算房屋價值與車位價值：

```text
房屋估值 = 預測每坪單價 × 房屋坪數
合理總價 = 房屋估值 + 車位估值
```

若原始紀錄無法可靠拆分車位價格或面積，必須標記處理規則，不可默默混入主要目標。

### 5.3 候選模型

1. 生活圈與產品類型的近期中位數基準。
2. Linear Regression 或 Ridge Regression。
3. Random Forest Regressor。
4. Gradient Boosting 類模型。
5. 第二階段選配 XGBoost 或 LightGBM。

正式模型由時間外測試表現、穩定性、推論速度及可解釋性共同決定，不預設最複雜模型獲勝。

### 5.4 驗證策略

- 依交易時間切割，較新的交易作為測試集。
- 檢查同一社區或建案的高度相似紀錄，降低資料洩漏。
- 指標至少包含 MAE、MAPE、RMSE 與 R²。
- 分別公布中古屋、預售屋、A17、A18、A19 和主要住宅類型的誤差。
- 與近期中位數基準比較；正式模型若無穩定改善，不上線取代基準。
- 保存模型、特徵版本、訓練資料期間與評估結果。

### 5.5 估價區間與解釋

輸出必須包含估價中位數與合理區間，區間可使用分位數模型、殘差分布或 conformal prediction 實作。特徵解釋使用特徵重要性或 SHAP；相似案例則使用經標準化後的特徵距離，並限制在相同交易類型與合理時間範圍內。

## 6. 系統架構

```text
內政部實價登錄／桃園開放資料／使用者輸入
                    ↓
          Python 下載、驗證與 ETL
                    ↓
       MySQL raw → clean → geo → feature
                    ↓
       中古屋模型／預售屋模型／模型登錄
                    ↓
              Flask REST API
                    ↓
       HTML + CSS + JavaScript + Ajax
                    ↓
  市場儀表板／條件估價／相似成交／LLM 摘要
```

Git、測試、Docker、日誌與 MLOps 橫跨所有層。各模組透過明確資料表、檔案格式或 API 契約溝通，使資料來源、模型與介面可獨立替換。

## 7. 介面設計

首頁採已批准的混合版型：

- 左側：A17～A19 市場地圖、生活圈指標與近期趨勢入口。
- 右側：中古屋／預售屋切換與快速估價表單。
- 下方：價格趨勢、交易量、產品結構、近期成交與資料說明。
- 導覽：市場行情、AI 估價、社區比較、模型說明；收藏功能留待後續。

估價結果頁依序顯示：合理總價區間、目前開價差距、可信度、主要正負因素、相似成交、模型與資料日期、限制聲明。重要證據必須先於 LLM 文字摘要呈現。

## 8. API 契約

- `GET /api/market/summary`：生活圈行情摘要。
- `GET /api/market/trends`：價格與交易量趨勢。
- `GET /api/transactions`：篩選後的歷史成交。
- `POST /api/valuations`：驗證輸入並執行估價。
- `GET /api/valuations/{id}`：取得估價、解釋與相似案例。
- `POST /api/reports`：依既有估價證據產生白話摘要。

錯誤回應必須使用一致格式，至少包含錯誤碼、使用者可理解的訊息及可修正欄位；不得把內部例外或密鑰回傳前端。

## 9. 異常處理與降級

- 官方欄位或檔案格式改變：更新中止並保留上一版正式資料。
- 新批次資料量、缺失率或極端值異常：隔離批次並產生品質報告。
- 地址定位信心不足：要求使用者選站或地圖位置，不假裝精確。
- 使用者輸入超出訓練範圍：標示低信心並解釋原因。
- 相似成交不足：逐步擴大時間或距離，並顯示實際條件。
- 模型服務失敗：退回近期中位數基準並標示降級模式。
- LLM 不可用：保留完整估價、圖表和結構化解釋。
- 資料過期：顯示最後更新日期與警示。

## 10. 測試策略

- 單元測試：民國日期、坪數、樓層、車位與文字欄位解析。
- 資料契約測試：必要欄位、型別、允許值與來源版本。
- 資料品質測試：重複率、缺失率、定位率及極端價格。
- 特徵測試：訓練與線上推論使用同一轉換管線。
- 模型測試：時間外誤差、分群誤差、基準比較和漂移。
- API 測試：正常、缺少欄位、異常值、低信心與服務降級。
- 端對端測試：從輸入條件到結果頁與相似成交完整流程。
- Docker 冒煙測試：全新環境可啟動資料庫、API 和前端。

## 12. 里程碑

### M0：資料可行性

- 可重現地下載桃園中古屋與預售屋資料。
- 統計 A17～A19 可辨識筆數、定位成功率及主要缺失。
- 產出資料品質報告並決定可用資料期間。

### M1：市場分析

- 完成清理流程、MySQL schema 與三生活圈判定。
- 完成混合首頁中的市場地圖、趨勢及近期成交。
- 中古屋與預售屋全程分開呈現。

### M2：AI 估價

- 完成基準及至少三種模型比較。
- 完成時間切割測試與各生活圈誤差報告。
- 顯示估價區間、相似成交、可信度及特徵解釋。
- 發布模型卡與限制說明。

### M3：完整網站

- 完成 Flask API、MySQL、HTML／JavaScript 前端。
- 完成錯誤處理、自動測試與 Docker 啟動。
- 完成 README、架構圖、畫面與操作影片。

### M4：上線能力

- 定期更新官方資料並具備失敗回復能力。
- 模型版本、效能與資料漂移監控。
- LLM 購屋報告、收藏、通知及雲端部署。

## 13. 第一版完成標準

1. 資料來源、清理和特徵流程可重現。
2. 中古屋與預售屋沒有混用正式模型。
3. 測試集依時間切割，且已檢查主要資料洩漏風險。
4. 每次估價都有區間、相似成交、可信度及資料日期。
5. 網站在資料、模型或 LLM 失敗時有明確且可用的降級結果。
6. 新使用者依 README 可啟動系統。
7. 面試時可在五分鐘內展示市場洞察、估價、證據與技術架構。
